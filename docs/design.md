# Nexus 设计讨论

状态：用户已于 2026-10-08 确认首版设计。本次仅做前置调研与 Spec，不编写插件或探针代码。项目目录为 `E:\Agent\dsh-nexus`，包名为 `dsh-nexus`，面向用户的名称为 Nexus。详细依据见 [调研](research/agent-result-delivery.md)、[词汇表](../CONTEXT.md)及 [ADR](adr/)。后续设计以本项目目录为准。

## 已确认

- Nexus 是独立的 DeepSeek Harness 插件，不修改 Qiyu 产品。首版覆盖 Harness 会话，跨 Codex、Claude Code 留待以后。
- 唯一主管使用同一个 Realtime 模型。主管负责理解、拆解、调度和检查结果，具体工作交给工作会话。
- Nexus 拥有完整操作权限，可以直接使用所有已有会话，无需逐个授权或人工审批。
- 所有工作会话进入全局观察范围，结果返回主管；不仅限于主管创建的子会话。
- 工作结果自动投递 Nexus。主管忙时在后续处理中接收，闲时唤醒；后续调度和是否、何时向用户汇报由 Nexus 根据上下文判断，不写死完成必播报或失败必插话等规则。语音层负责正常轮次与打断，挂断后保持纯文字输出。
- 用户明确指令优先，采用原生运行中引导，由 agent 自己调整执行。不增加指令版本仲裁、意图分类或自动强制取消。
- 挂断后主管继续工作，在同一个主会话输出文字，不生成或播放语音，不切换另一个文本模型。
- 是否追加修复、继续审查、结束任务或报告阻塞，由 Nexus 根据用户目标、上下文与实际结果自行判断，不在 Host 写死循环流程或迭代轮数。
- 会话保存、恢复和重启行为沿用 Harness 原生机制，不另造一套重启后自动续跑机制。
- Harness 原生侧栏提供固定 Nexus 入口，进入主管主会话，在其中开始或挂断语音；工作会话继续使用 Harness 原生界面。
- 提供默认关闭的“启动 Harness 后自动进入 Nexus 语音”选项，开启后每次 Harness 进程启动自动尝试接通一次。主动挂断后保持文字模式，刷新页面或切换会话不会重新开麦；用户可手动再次接通。该选项不是系统登录后自动启动 Harness。
- 首版沿用现有适配的 `qwen3.8-omni-flash-realtime`，通过 DashScope Realtime WebSocket 直接处理语音与文字。复用已核实的协议经验，Nexus 的主管提示词和工具按本项目职责设计。
- 当前项目只有设计文档，尚无插件实现；Harness 兼容版本和准确型号的纯文字工具调用链路仍需验证。实现路径见 [实现设计](implementation.md)。

## 首版验收场景

1. 用户在 Nexus 主会话中要求一个已有工作会话修复报错，再让另一个工作会话审查。
2. Nexus 可以操作已有修复会话，并安排审查会话；工作执行期间用户仍可与 Nexus 通话。
3. 用户途中修改要求，新指令进入相关会话的上下文，工作 agent 与 Nexus 根据新要求调整后续工作。
4. 用户挂断，工作会话和主管继续运行。主管处理执行结果和后续调度，主会话有文字输出且无语音。
5. Nexus 根据任务和结果自主决定后续动作，最终在主会话报告修改及验证结果；验收不要求固定修复与审查循环。

## 后续技术验证

- 核实主会话如何接入 Realtime 主管，以及如何保留原生消息记录，避免另设一个原生模型主管。
- 核实首版兼容的 Harness 版本、全部会话控制与结果事件接口，以及当前型号的纯文字输出和工具调用联合链路。
- 验证客户端就绪、系统麦克风许可、音频播放、断线重接与关闭客户端后 Host 的文字工作路径。
- 工作区和并发任务的具体安排由 Nexus 理解任务后决定，Host 不另设固定工作流。
