# 12：主会话自动与手动上下文压缩

**要构建的行为：** 主会话交流历史超过 Nexus 设置的预算时，在主管轮次之间按 Harness 原生方式自动压缩；用户也可在主会话输入 `/compact` 手动压缩。压缩后文字与语音续答使用摘要与近期原文，主管每轮记录实际 token 用量。

**阻塞于：** 10：断线或关闭客户端后保留主管工作（同改主管连接与重放，需等其收尾）。

**状态：** 已实施，待用户验收（2026-10-10）。受控自动验证见 `docs/verification/12-supervisor-context-compaction.md`；准确型号与实际摘要模型的一次真实压缩、Desktop 中 `/compact` 与设置待用户实机验收。

**范围与约束：** 复用原生压缩的摘要、保留近期原文与落盘语义，不另建 Nexus 专用摘要或状态表。压缩预算默认 128k token，与摘要模型（默认沿用普通会话的默认模型）一同放在 Nexus 原生设置，用户可改；不以模型约 1M 的上下文窗口为触发依据。压缩只在主管轮次之间发生，不打断正在说的话或执行中的工具；通话中在轮次边界重建 Realtime 上下文，状态如实显示。文字模式每轮重建连接、全量重放的费用本票不处理，只记录用量供后续决定。不补做在途工作专门验收（用户裁定由摘要负责）。

已知事实（2026-10-10 只读核查，实现时复核）：
- 主管自有循环不经过原生压缩挂载的 agent 步前与请求失败钩子；其模型路由 `dashscope-realtime` 在 Host 中没有登记的模型适配，查不到上下文窗口，也无法作为摘要模型。
- 主管的预设在首轮工作时才延迟绑定，客户端缓存的命令列表因此没有 `/compact` 且不会刷新。
- 主管 assistant 消息未记录 usage；Realtime `response.done` 的用量被忽略。
- 压缩后检查点以用户消息替换被压缩区间；重放给 Realtime 时会带来源前缀，未闭合的工具调用不能被切开；`nexus-work-result`、`nexus-user-input` 等来源在摘要中应保持含义。
- 上一代 Realtime 模型文档提到会话最大轮次限制，新型号是否同样限制、是否影响重放未核实。

- [ ] 主会话超过预算后，在下一个轮次间隙自动压缩；原生记录出现完整的压缩起止与检查点，原有记录仍可查看。（受控自动验证通过。）
- [ ] 主会话一打开，输入 `/compact` 即出现在命令列表，执行成功并使用设置中的摘要模型。（受控 Host 与浏览器验证通过；Desktop 待实机。）
- [ ] Nexus 设置中可修改压缩预算与摘要模型，跨重启保存，修改后按新值生效。（浏览器与新 Host 进程验证通过；Desktop 待实机。）
- [ ] 压缩后文字续答与新接通的语音只重放摘要与近期原文，主管仍能正常理解后续工作结果并派活。（受控端点验证重放内容与派活；真实模型理解待真实压缩验收。）
- [ ] 通话中触发压缩时不打断正在播放的回复或执行中的工具，重建期间状态如实显示。（受控通话验证通过；物理音频未实机。）
- [ ] 每轮主管回复记录实际 token 用量，原生用量与上下文压力显示真实数据。（受控用量验证通过；DashScope 实际 usage 字段形状待真实端点核对。）
- [ ] 压缩失败（摘要模型不可用、调用失败）时如实记录并保持原上下文继续工作，不生成假摘要。（受控失败模型验证通过。）
